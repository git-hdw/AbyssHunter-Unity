# 《深渊猎手》项目愿景与开发路线

建立日期：2026-11-02；最近核对日期：2026-11-23。

这是产品目标、阶段完成标准与阶段进度的持久入口。[AGENTS.md](../AGENTS.md) 规定执行规则，[PROJECT_CONTEXT.md](PROJECT_CONTEXT.md) 记录实际架构与技术决策，[HANDOFF.md](HANDOFF.md) 记录逐次验证、证据和未完成项。目标不等于已经实现；文档与代码冲突时先核对当前工程，再修正文档，不能把现状悄悄改成更低的目标。

## 1. 最终定位与核心体验

AbyssHunter（深渊猎手）是一款 Unity 6.3 + URP 的单人 3D 俯视角暗黑奇幻动作冒险游戏，交付目标为 Windows x64 高质量独立游戏作品集 Demo。当前指定编辑器为 6000.3.23f1，依赖版本以工程配置为准，不为目标整理升级依赖。

最终 Demo 应具备完整关卡流程、精致场景美术、流畅战斗操作、明确敌人机制和沉浸式探索氛围。源码、实际运行包和演示素材共同证明品质。

**探索危险遗迹 → 遭遇敌人 → 观察攻击前摇 → 闪避与反击 → 获取资源 → 完成关卡目标 → 继续深入。**

玩家应通过观察、操作和策略逐渐熟练掌握战斗；探索和资源应服务于关卡目标。进度以体验改善衡量，不以系统、模型或代码数量衡量。先打磨现有两关与战斗基础，不盲目扩大敌人、技能、存档、联网或其他系统的范围。

现有边界继续有效：账号用于认证；本机按账号保存解锁与最佳成功用时；每次远征独立重置生命/背包；没有中途存档或云存档。长期目标不自动授权修改这些规则。

## 2. 场景美术目标：当前最高优先级

统一采用 **Stylized Dark Fantasy + Low Poly**，与当前猎手和骷髅角色协调。使用模块化建筑、环境叙事、电影感灯光和适度魔法特效；保留战斗轮廓及攻击预警的辨识度。

| 关卡 | 建筑与环境目标 | 区域记忆点与引导 |
| --- | --- | --- |
| 第一关：[SampleScene](../Assets/Scenes/SampleScene.unity)，沉没遗迹追猎 | 古老、破败、神秘的沉没遗迹；残破石柱、断墙、古建筑、石桥、微弱火光 | 破败前厅 → 悬空桥梁 → 神秘祭坛；冷蓝灰环境、局部暖火与青色符文形成引导 |
| 第二关：[AbyssDepths](../Assets/Scenes/AbyssDepths.unity)，裂隙回廊 | 危险、壮观的深渊浮岛；悬空平台、断裂岩层、漂浮残迹、紫色深渊能量与晶体设施 | 稳定起航区 → 压迫感通路/守望台 → 核心祭坛；青蓝设施、紫色裂隙和橙金目标建立主次 |

两关共用材质尺度、模型比例、石材处理和特效强度等美术语言，同时保留不同建筑特色、色彩氛围与视觉记忆点。统一不等于复制同一套构图。

优先使用授权明确、风格一致的实际模块化 3D 模型；不持续用 Cube、Cylinder 等基础几何体拼复杂建筑，也不靠重复尖刺、碎石或换色掩盖造型问题。必要的碰撞代理和简单造型可以沿用，复杂建筑应有经过设计的轮廓、比例、结构、破损与材质变化。

每个重要场景要有清晰视觉焦点、前中远景层次和有效灯光引导。雾、粒子和 Bloom 用于衬托焦点，不能让道路、敌人、攻击范围或交互目标消失。悬空与危险感来自断层、落差和空间构图，不通过新增不可见障碍或破坏通路实现。

第三方资源须记录作者、来源、版本、许可和公开分发范围；保留许可与必要归属。未确认源资产可公开再分发时，不上传 GitHub。新资源先做一个可验收区域，再逐区推广，避免批量替换造成尺度、碰撞、导航或风格失控。

## 3. 核心玩法与战斗目标：同样重要

操作简单、反馈明确、具有技巧空间。沿用现有架构，逐项提升：

1. 移动、转向、攻击和闪避的响应与衔接，避免输入被意外吞掉或动画长期锁住操作。
2. 普通攻击的命中反馈：音效、粒子、击退、短暂停顿与适度镜头反馈相互匹配，避免靠强烈震屏掩盖打击感不足。
3. 敌人攻击前摇、范围、动作衔接、命中时机与后摇破绽一致；可读的危险信号对应可预测的伤害。
4. 普通敌人与精英/重锤敌人有明确行为差异，玩家需要选择接近、躲避与反击时机。
5. 战区空间、敌人组合和连续遭遇的节奏合理，有躲避重击的余地，不用拥堵和遮挡制造难度。
6. 探索、资源拾取、补给、交互与关卡目标形成联系，奖励冒险和路线判断。

不能只提高敌人生命或伤害来增加难度。先评审已有战斗手感和机制，再决定是否需要新敌人、技能或复杂系统。攻击动画事件去重、重击阶段时钟、闪避取消待命中攻击、池化恢复等兼容要求继续执行，详见 AGENTS 和 PROJECT_CONTEXT。

## 4. 关卡设计与可读性标准

每关必须具备明确进入区域和视觉引导、至少一个辨识度强的主战场、有节奏变化的探索/过渡空间、重要目标区域或最终遭遇，以及合理难度递进和阶段反馈。

优先用空间、建筑、灯光、敌人布局与交互反馈引导玩家，而非增加大量文字说明。前进、绕行、回程、危险边缘和目标位置应能在游戏镜头中识别；装饰不遮挡敌人或预警，不改变已验证的行走区与平台连通关系。

本轮基线已有两关三段遭遇和“清敌 → 取核 → 返回 → 点灯 → 撤离”流程；清场不等于成功。第一关 6 枚碎片投入 4、剩 2；第二关 9 枚投入 6、剩 3。地图与流程调整属于后续具体任务，不能借长期目标整理擅自重设计。

## 5. 阶段路线与完成标准

阶段顺序为美术 → 战斗 → 关卡体验 → Demo 收尾。阶段之间允许处理必要的阻断性修复，但一次迭代只选一个主题，不能把每个阶段同时开工。已有基础不意味着整个阶段通过。

### 阶段一：场景美术升级（整体品质待验收）

工作：引入统一模块化模型；改善两关建筑、材质和空间层次；优化灯光、雾、晶体设施与祭坛；消除明显程序生成感。

完成标准：

- 两关入口、主战区、桥/过渡和祭坛均具有完成的构图与不同记忆点，复杂建筑不再主要依靠基础几何体重复堆砌。
- 模型比例和材质密度协调，新旧地面自然衔接，破损有结构依据；无明显穿插、悬空接缝、贴片感、缺材质或粉色错误 Shader。
- 从实际 Game 镜头检查静态截图和连续移动：道路、玩家、敌人、预警、掉落及交互目标清晰；高建筑的遮挡处理有效；雾和辉光不过度覆盖战斗。
- 分别保存两关入口、战斗、桥、祭坛、取核和归途的对照证据；Scene 视图不能单独证明美术完成。
- 生成源同步，重复生成不丢失成果；原碰撞、Transform、玩法引用与 NavMesh 保留或按获批范围验证迁移；主路、侧路与回程实际可通行。
- 记录固定路线下绘制、三角形、内存和帧时间相对基线的变化；新增模型不得明显损害流畅度。需要设备与分辨率明确的 Player 采样，不能用 Editor 单帧统计宣布成品性能通过。

### 阶段二：核心战斗手感（人工验收待确认）

工作：命中反馈、闪避、敌人动作/预警、战斗音效和特效；优先打磨现有普通敌人与重锤机制。

完成标准：

- 通过实际输入完整游玩，两类敌人的前摇、命中、后摇能被观察并利用，合理闪避后能反击；不靠反复点击或单纯堆数值取胜。
- 动画、范围预警和伤害时机一致，无重复伤害、闪避残留攻击、池化恢复异常；命中反馈与音画同步且不妨碍观察。
- 移动/攻击/闪避及暂停、背包、死亡、重开之间的衔接稳定，时间状态和输入阻断正确。
- 相关重击、远征、中文展示回归通过，并完成真实 Player 的人工战斗与听音评审。受控击杀/无敌夹具只能证明逻辑。

### 阶段三：关卡体验提升（当前进行中）

工作：敌人组合与节奏、探索引导、环境叙事、目标反馈、区域过渡；适量增加有价值的互动。

完成标准：

- 两关均有清晰入口、主战区、过渡与目标区，遭遇难度和压力有变化；主路与可选补给路线有明确价值。
- 玩家能依据环境和即时反馈找到前进方向、取核和回程目标；不依赖大量新增文字解释流程。
- 清场未撤离不解锁，死亡不计成功；取核、点灯、撤离、成功用时、选关解锁与当前关重开行为正确。
- 路线、敌人布局和交互的改变有实际游玩证据，且保持背包物品身份、掉落、导航与关卡目标兼容。

### 阶段四：作品集 Demo 完成

工作：统一 UI/音效和整体体验，优化性能，完整流程测试，制作 Windows 发布版本与演示素材。

完成标准：

- 从 MainMenu 到认证、选关、两关完整流程、失败/成功重开、返回和换账号均实际验收；真实 PlayFab 注册/登录及恢复邮件验收独立记录，不能以替身测试充数。
- Unity 编译/Console、场景/Prefab 引用和相关回归通过；按既有单次构建顺序重建 Addressables，真实 Player 验证掉落、物品身份及两关撤离流程。
- 先明确目标硬件、分辨率与帧率/内存预算，再以固定路线的 Player 性能结果验收；当前尚无这些成品验收数据，不凭空填写达标数值。
- 完成人工画面、战斗、听音和全流程评审；已知问题有修复结果或明确接受范围，不能把未验证项写成已通过。
- 形成可复现的 Windows x64 包、中文说明、许可清单和实机演示素材；版本、报告和包对应。发布须获得当次授权，备份分支不等于发布，不覆盖 v0.2.0 基线。

## 6. 每次迭代的执行与进度维护

用户要求“继续优化 AbyssHunter”时，依次执行：

1. 阅读 AGENTS、本愿景、PROJECT_CONTEXT 与 HANDOFF，查看 Git 分支、状态和最近提交。
2. 用实际场景、资源、生成脚本和运行证据核对进度，判断当前最影响品质的问题；先确认已有功能，避免重复实现。
3. 选择一个明确主题，说明本次目标、验收方式和不应修改的范围。
4. 在任务授权范围内实际修改；复用架构和资源，保持模块化；生成场景同步生成源。必要的核心改动先核对调用、序列化引用及回归范围。
5. 按“批量开发、集中验证”完成整批代码/场景/资源集成后，统一执行编译、资源引用、Game 视图、实际运行及必要回归；开发中仅局部检查阻塞错误。集中发现的问题统一修复后按影响范围复验，避免逐功能重复完整测试。已有 Editor 时复用，不另开同工程批处理。无法验证时明确说明缺失证据。
6. 汇报成果、实际验证、尚存问题和下一步，不以计划代替实现或扩大当前任务。
7. 在本文件更新阶段/任务状态，在 HANDOFF 写日期、范围、报告与限制；技术结论更新 PROJECT_CONTEXT。仅文档变更核对事实、路径、链接及差异格式，无须重新打包。

状态使用：**已完成并验证 / 已实现待验证 / 正在处理 / 待实现**。进度表是当前摘要，不覆盖历史证据。项目最终完成不等于本愿景文档已经建立；未来每次迭代继续按本路线推进。
